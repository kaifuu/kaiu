## 二、问题诊断

### 2.1 质量保障（严重）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| Q1 | **后端零自动化测试** | `backend/src/test` 目录不存在（`spring-boot-starter-test` 依赖已引入但未使用） | 16,102 行代码无回归保护，任何改动靠人工点击验证，重构风险极高 |
| Q2 | **仅前端冒烟测试** | `frontend/scripts/ui_check.mjs` 单文件 | 只覆盖 UI 存在性断言，业务逻辑正确性（预警判定、围栏算法、指令状态机）无验证 |
| Q3 | **核心算法无边界测试** | 围栏空间判定、轨迹预测外推、电量骤降窗口计算均为纯逻辑，最适合单测却无覆盖 | 阈值调整、算法迭代时容易引入静默错误 |

### 2.2 数据与容量（严重）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| D1 | **轨迹表无限增长** | `DeviceService.java:327-337` 每次 OSD 上报（含经纬度）即 `trackMapper.insert()`，全库无任何清理/归档/分区策略 | 设备 1Hz 上报 → 单机 **86,400 行/天**、约 3,150 万行/年；查询随数据量线性劣化，最终拖垮库 |
| D2 | **历史架次无轨迹归档** | 轨迹按「设备 SN + 时间窗」存储（`track()` 接口用 `minutes` 参数），未按架次（flightId）归档 | 历史架次回放只能**前端合成轨迹**（`ScreenFlights.vue` 的 `synthTrack()`），回放非真实数据，无法作为取证依据 |
| D3 | **无版本化数据库迁移** | `backend/sql/schema.sql` 全 `IF NOT EXISTS` + `config/SchemaMigration.java` 中硬编码 `ALTER`（注释自述因脚本执行器按 `;` 切分才放 Java） | 多环境升级无版本追踪、无回滚路径；DDL 与代码版本脱钩 |
| D4 | **种子数据与业务代码耦合** | `config/DataInitializer.java` 承担演示数据注入 | 生产部署需手工规避种子注入，易误灌测试数据 |

### 2.3 工程化与运维（严重）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| O1 | **无可观测性** | `application.yml` 仅 `logging.level.com.emergency: info` 一行，无 Actuator / 健康检查 / 指标采集 | 生产排障只能翻日志文件；无健康探针，容器编排无法做存活判定 |
| O2 | **无容器化交付物** | 全仓无 `Dockerfile`；`docker-compose.yml` 仅启动 PostgreSQL | 后端与前端无标准镜像，部署依赖手工 `mvn spring-boot:run` / `npm run dev` |
| O3 | **无 CI/CD** | 无 `.github/`、`Jenkinsfile`、`.gitlab-ci.yml` 等流水线配置 | 构建、测试、回归全靠本地手工执行，无质量门禁 |
| O4 | **单环境配置** | 仅一份 `application.yml`，无 `application-dev/prod.yml` | 开发与生产共用配置，切换靠改文件 |
| O5 | **密钥明文入库** | `application.yml`：数据库密码 `inspect123` 明文；JWT secret 虽有环境变量回退但**默认值硬编码** | 违反安全基线，代码泄露即凭据泄露 |

### 2.4 性能（中等）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| P1 | **无缓存层** | 全库无 Redis / Caffeine / `@Cacheable` | 每个大屏请求都全量聚合查询打库 |
| P2 | **高频轮询压库** | 8 个子屏各自轮询：设备屏 5s、其余 30s（`frontend/src/views/screen/*.vue` 共 24 处 `setInterval`） | 多客户端并发时，聚合查询量成倍放大；无缓存兜底 |
| P3 | **大屏接口全量重算** | `/screen/*` 每次请求重新统计（如 `ScreenService` 的 byStatus/byDept 分组） | 数据量大后响应时间不可控 |

### 2.5 安全合规（中等）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| S1 | **入参校验几乎为零** | 全仓仅 **1 个文件** 使用 `jakarta.validation` / `@Valid`（依赖已引入） | 198 个接口入参靠 Service 手工判空，脏数据易入库 |
| S2 | **无接口限流** | 全仓无 RateLimit / 令牌桶实现 | 登录、验证码、导出等接口可被高频刷取 |
| S3 | **登录无失败锁定** | `AuthService` 中无失败计数 / 锁定逻辑，验证码是唯一防线 | 撞库攻击仅需绕过验证码环节 |
| S4 | **审计日志覆盖面待验证** | 存在 `SysLog` 实体与页面 | 需确认是否覆盖仿真指令下发、策略编辑等敏感操作 |

### 2.8 核心能力缺口（最高优先级）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| C1 | **算法识别为合成实现** | `service/AiAlarmGenerator.java` 类注释自述「平台侧算法（视频流/传感数据分析）没有真实 CV 推理可接」，告警由 `@Scheduled` 按节流窗口合成；6 类算法中仅臭气由真实站点读数驱动 | 需求 A 2.8 的六类识别能力**实质未实现**——演示可过，验收与长期运营不可过 |
| C2 | **无样本集与训练闭环** | 全仓无样本管理、标注、训练、评估相关模块 | 需求 A 2.9.2 明确要求「构建样本数据集 + 基于深度学习模型训练与优化」，当前无落地路径 |
| C3 | **零真机运行数据** | 设备、遥测、轨迹、媒体全部来自 `tools/dji-sim/sim.js` | 无真机验证，延迟/精度等指标无实测依据；无实战案例支撑 |
| C4 | **动态阈值无冷启动方案** | 需求 A 2.9.3 依赖历史巡检数据积累，而系统尚无真实运行数据 | 存在「要数据才能建模、要建模才有数据」的死循环 |
| C5 | **无法获取视频帧** | `VideoChannel` 仅存拉流地址（FLV/HLS/RTMP/GB28181 协议枚举 + URL 字段），全仓无拉流/解码代码（无 FFmpeg / JavaCV） | 即使接入算法引擎也**没有输入源**——这是算法落地的前置阻塞项 |

> **C1–C4 是需求 A 的验收命门**：页面与业务流程已完备，但核心识别能力缺失。
> 第 4 章的 **P3-1 ~ P3-3** 为专门解决该缺口的必做项，优先级高于其余功能升级。

## 三、升级目标与原则

### 3.1 升级目标

| 目标 | 量化指标 |
|---|---|
| **可回归** | 核心业务逻辑单元测试覆盖率达 60%+，CI 自动门禁 |
| **可承载** | 轨迹表年增 3000 万行下查询 P95 < 200ms；大屏接口 P95 < 500ms |
| **可运维** | 健康检查 + 指标采集 + 标准镜像，一键部署 |
| **可扩展** | 新增一个业务子系统的公共能力复用率 > 70% |
| **可合规** | 密钥零硬编码，接口入参 100% 校验，敏感操作全审计 |
| **可识别** | 六类算法接入真实推理（非合成），每类准确率达约定门槛（建议 ≥85%），样本集与模型版本可追溯 |
| **可真机** | 至少完成 1 次真机全链路架次（航线下发 → 数据采集 → 算法识别 → 告警 → 工单办结） |

### 3.2 改进原则

1. **不停机演进**：数据库变更全部向后兼容（先加列、后回填、再切读），不阻塞现有业务。
2. **小步快跑**：每项改进独立可交付、可验证，避免大爆炸式重构。
3. **先筑基后扩展**：测试与数据治理优先于新功能开发——否则新功能同样缺乏保障。
4. **复用优先**：公共能力沉淀到平台层，两个业务子系统共用。

## 四、改进项清单

> 优先级：**P0** 阻塞交付（1 个月内）/ **P1** 影响稳定（1–2 个月）/ **P2** 提升质量（2–3 个月）/ **P3** 能力建设与功能升级（3–7 个月）

### P0 · 工程质量筑基

| 编号 | 改进项 | 具体措施 | 工作量 | 收益 |
|---|---|---|---|---|
| P0-1 | **测试体系** | 引入 JUnit 5 + Testcontainers；优先覆盖纯逻辑：围栏空间判定、轨迹预测外推、电量骤降窗口、指令状态机、JWT 校验 | 15–25 人日 | 重构有安全网，回归自动化 |
| P0-2 | **版本化迁移** | 引入 Flyway，将 `schema.sql` 拆为 `V1__init.sql`、`V2__*.sql`；废弃 Java 内硬编码 `ALTER` | 3–5 人日 | 多环境升级可追踪、可回滚 |
| P0-3 | **配置分环境** | 拆 `application-dev.yml` / `application-prod.yml`；DB 密码、JWT secret 全部改环境变量。⚠️ **仅改 yml 不够**——`@ConfigurationProperties` 绑定下占位符解析失败不抛异常，会把字面量 `"${JWT_SECRET}"` 或字段默认值当密钥，应用带着**可预测密钥静默启动**（实测确认）。必须配 `JwtSecretValidator` 显式兜底 | 2–3 人日 | 消除密钥硬编码 |
| P0-4 | **种子数据隔离** | `DataInitializer` 加 `@Profile("dev")` 或开关，生产默认不注入演示数据 | 1 人日 | 避免误灌测试数据 |

## 七、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 轨迹表改造涉及存量数据 | 迁移失败或数据丢失 | 先建新分区表 → 双写 → 回填 → 切读 → 保留旧表 1 个月再删 |
| 引入测试体系初期拖慢交付节奏 | 短期产出下降 | 只对**核心纯逻辑**补测，UI 层仍靠冒烟；不追求形式化覆盖率 |
| 缓存引入导致数据不一致 | 大屏显示滞后 | 实时遥测不走缓存；聚合数据 TTL ≤ 30s，与轮询周期对齐 |
| 第三方集成依赖外部系统进度 | 阻塞阶段四 | 先做接口契约与 Mock 联调，外部就绪后切换 |
| 仿真反无子系统体量大 | 挤压既有改进 | 独立立项、独立排期，仅复用平台底座，不与本计划耦合 |
| 前端组件拆分引入回归缺陷 | 页面功能异常 | 拆分前后均跑 `ui_check.mjs`，逐组件对比截图 |
| **算法精度不达标**（C1/C2） | 需求 A 无法验收 | ① 先用开源模型快速验证链路（P3-1）② 同步启动样本采集，**样本积累是长周期工作，第 3 月即须开始** ③ 与甲方约定分阶段精度门槛，避免一次性卡死 |
| **真机与空域审批延误**（C3） | 阶段四阻塞 | 第 3 月启动协调；未到位时用 `MockEngine` + 模拟器继续推进其余改进项，真机联调独立并行 |
| **标注人力不足**（P3-2） | 样本集建不起来 | 优先标注高频场景（烟火/泄漏）；引入半自动预标注（模型初筛 + 人工修正）降低标注量 |
| **实时性指标不达标**（P3-10） | 仿真反无验收失败 | 第 1 个子项即做延迟基线实测；操控链路采用独立线程/无锁队列，必要时下沉到本地服务 |
| **视频帧管线缺失**（C5） | 算法引擎无输入，P3-1 无法启动 | 先做「媒体文件 → 解码 → 抽帧」事后分析链路（不依赖流媒体协议栈），实时流抽帧后置 |
| **部分类别无开源模型**（P3-2） | 覆盖膜/烟羽/泄漏等类别精度难达标 | 按类别分别约定精度门槛与交付时间；优先保障高频场景（烟火/泄漏），低频类别分阶段交付 |
| **算力不足**（P3-1 前置②） | 多路推理跑不动 | 先做算力基线测定再定部署方案；不足时降并发路数或改抽帧频率，必要时申请 GPU |
| **溯源精度预期偏差**（P3-8） | 验收被卡 | 提前把口径谈成「候选区域 + 置信度」，并提供扩散模拟可视化佐证 |
| **离线环境与云端 API 冲突**（P3-9） | 功能不可用 | 默认本地模型部署，云端 API 仅作可选开关 |
